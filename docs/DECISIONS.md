# Decisions

Decisions taken during implementation that are not spelled out in SPEC.md. Architectural decisions D1–D5 live in SPEC.md §4.6 and the SDD.

| # | Date | Decision | Rationale |
|---|------|----------|-----------|
| I1 | 2026-10-08 | All backing services (PostgreSQL, Redis, OTel collector, Prometheus) run only via `docker compose`; nothing is installed on the host. Host-side `pytest` uses the compose `db` service published on `localhost:5432` (`make deps` / `make test` start it). CI uses the same compose services. | Single source of truth for dependency versions; reproducible from a clean clone. |
| I2 | 2026-10-08 | ~~Resolved in milestone 4: the setting was removed once `catalog_gateway.py` existed.~~ `.importlinter` contract `catalog-only-via-gateway` sets `unmatched_ignore_imports_alerting = none` because `catalog_gateway.py` does not exist until milestone 4. To be tightened back to the default once the gateway exists. | import-linter otherwise errors on an ignore rule that matches nothing. The contract itself is not weakened. |
| I3 | 2026-10-08 | The Docker image installs the dev dependency group so tests and lint can run in-container; the runtime command is `gunicorn`. | Simplicity for the assessment; a slim prod stage is a later optimisation. |
| I4 | 2026-10-08 | Interface and infrastructure are modelled in import-linter as independent sibling layers under `contexts.scheduling`, with `container` as an optional top layer. | Encodes "interface must not import infrastructure except through container.py" (§8). |
| I5 | 2026-10-08 | Added domain error `CancellationNotAllowed` (code `cancellation_not_allowed`). The "cancel only before start" rule (A19) is enforced by `Appointment.cancel(now)`. | §14.2 defines the code but §4.3's error list omits it; the rule is business logic, so it belongs in the aggregate. |
| I6 | 2026-10-08 | `AppointmentRepository` gains `save(appointment)` alongside `add`, `get`, `vehicle_has_overlap`. | Cancellation must persist a state change; `add` stays insert-only so it can translate exclusion violations. |
| I7 | 2026-10-08 | Technician "load that day" (A9) = number of confirmed appointments within the dealership's opening window of the slot's local date. `ResourceRepository.find_available_technicians` takes that window as `load_window`. | Simplest meaningful measure; the allocator only sees an integer and stays agnostic. |
| I8 | 2026-10-08 | Typed ids are `typing.NewType`; `shared_kernel` holds only `DomainEvent` and `Clock`. No Entity/ValueObject base classes: frozen dataclasses already give value semantics. | Avoids the over-abstraction §4.7 warns about. |
| I9 | 2026-10-08 | The 15-minute grid (A7) is checked on UTC. | Every real IANA offset is a multiple of 15 minutes, so UTC and local grids coincide. |
| I10 | 2026-10-08 | Domain errors carry their §14.2 `code` string; the HTTP status mapping stays in the interface layer. Ruff `N818` (Error suffix) is ignored for `domain/errors.py` only. | Names come from the ubiquitous language (§4.3). |
| I11 | 2026-10-08 | If `open_time`/`close_time` fall in a DST gap, `zoneinfo`'s default `fold=0` resolution applies. | Edge case outside the seeded data (08:00/09:00 openings); documented rather than special-cased. |
| I12 | 2026-10-08 | `CatalogGateway` returns Scheduling-owned value objects (`ServiceOffering`, `DealershipCalendar`, `CustomerRef`, `VehicleRef`) defined in `domain/model/references.py`. Vehicle ownership (A8) is `VehicleRef.ensure_owned_by`, a domain rule. | ACL per §4.1. Keeps the ownership rule out of handlers and views. |
| I13 | 2026-10-08 | Retry semantics: `BOOKING_MAX_RETRIES=3` means 3 retries after the first attempt (4 attempts total), each preceded by a jittered 10–50 ms sleep. When retries run out, the handler raises `NoCapacityAvailable`. Each retry re-runs the vehicle check and allocation against fresh state, so a lost race usually resolves to another bay/technician or to a precise `no_capacity`/`vehicle_already_booked`. | "Retry cap of 3" (§2.1), and "retry from step 3 (max 3)" (§4.5). |
| I14 | 2026-10-08 | `BookAppointmentHandler` returns the full 201 shape (`AppointmentDetails`, with names). Names come from catalog lookups already made and from the bay/technician entities the allocator chose, so no extra query is needed. `CancelAppointmentHandler` returns nothing (superseded by I18). | The command result is exactly what idempotency (§14.5) must store and replay. |
| I15 | 2026-10-08 | A repeated cancel is detected via the aggregate's `AppointmentAlreadyCancelled`. The handler turns it into a no-op that returns the original result (no save, no event). | A19: repeated cancellation is idempotent, yet the aggregate still guards its state transition. |
| I16 | 2026-10-08 | Application ports defined now: `UnitOfWork`, `CatalogGateway`, `EventPublisher`, `Clock` (re-exported from `shared_kernel`). `IdempotencyStore`/`AvailabilityCache` and the cross-cutting decorators are added in the milestones that use them (6, 7, 8). The unknown-reference error is `application.errors.NotFoundError` (code `not_found`). | No speculative interfaces. `NotFoundError` is not a spec-mandated name, so it takes the conventional suffix. |
| I17 | 2026-10-08 | Handlers take `sleep` and `new_id` callables (defaulting to `time.sleep` and `uuid4`). | Deterministic tests without a DI framework (§4.7). |
| I18 | 2026-10-08 | **User direction: the API follows RESTful conventions.** `DELETE /appointments/{id}/` returns `204 No Content` with an empty body, both for the first and repeated cancels. This overrides SPEC v1.0 §7 rule 12 ("repeat `DELETE` → `200`"); SPEC bumped to v1.1. `POST` returns `201` with a `Location` header. Unknown id → `404`; at/after start → `422`. `CancellationResult` DTO removed. | Requested by the user; standard HTTP semantics for a delete-style cancel. |
| I19 | 2026-10-08 | Service bays, technicians and skills are persisted by Scheduling (Django app label `scheduling`), since they are Scheduling's domain entities. Catalog holds dealerships, service types, customers and vehicles. Scheduling's ORM points at Catalog tables with string FKs (`"catalog.Customer"`), so no Catalog code is imported outside `catalog_gateway.py`. | §4.1 context split and the "Catalog only via gateway" contract. |
| I20 | 2026-10-08 | Seeding is split per context: `seed_catalog` (Catalog) and `seed_resources` (Scheduling). `seed_demo` (in Catalog, per §11) composes them by command name via `call_command`. Rows use the stable ids of §14.7, the seed is idempotent (`update_or_create`), and sequences are reset afterwards. | Neither context imports the other's models. The spec's examples (`dealership_id=1`, …) work verbatim. |
| I21 | 2026-10-08 | ORM classes are named `*Record` with explicit `db_table`s (e.g. `scheduling_appointment`). | Avoids confusion with the domain's `Appointment`/`ServiceBay`/`Technician` (D3). |
| I22 | 2026-10-08 | Constraints beyond §5: `cancelled_at_matches_status` and `time_range_half_open_non_empty` (CHECK) on appointments, unique bay name per dealership, Catalog CHECKs (`close_time > open_time`, `duration_minutes > 0`), and model validators for VIN/skill/IANA timezone. All FKs use `PROTECT`. | Cheap integrity guarantees; never retried since they are not SQLSTATE 23P01. |
| I23 | 2026-10-08 | `DjangoUnitOfWork`: `commit()` only marks success, and the `transaction.atomic` block commits on exit. Each `add` runs in its own savepoint, so a rejected insert leaves the connection usable. Per-call state is thread-local, so one instance can serve concurrent threads. `AppointmentRepository.get` uses `SELECT … FOR UPDATE` so concurrent cancels serialise. | Spec pitfalls (§10): explicit savepoints, no reliance on `ATOMIC_REQUESTS`. |
| I24 | 2026-10-08 | Only SQLSTATE `23P01` (exclusion_violation), read from the psycopg error behind Django's `IntegrityError`, is translated to `ResourceConflict`. Every other `IntegrityError` propagates unchanged. | §10 pitfall; covered by a test that inserts a duplicate primary key. |
| I25 | 2026-10-08 | Added runtime dependency `django-stubs-ext` and call `monkeypatch()` in settings. | Lets admin classes use typed generics (`ModelAdmin[Model]`) under `mypy --strict`; official django-stubs approach. |
| I26 | 2026-10-08 | The Appointment admin is read-only (no add/change/delete). | Bookings must go through the domain rules; admin edits would bypass them. |
| I27 | 2026-10-08 | Interface views get their use cases from `interface/api/dependencies.py` (a `SchedulingUseCases` Protocol plus `install_use_cases`). `config/urls.py` installs `container.get_container` as the provider. The interface layer never imports `container.py`. | The M1 layer contract puts `container` *above* `interface`, while §4.2 says views "obtain handlers from" the container. CLAUDE.md forbids editing `.importlinter` to make checks pass, so the dependency is inverted instead. Views still receive container-built handlers. |
| I28 | 2026-10-08 | The idempotency header is validated in M5 (required, 1–255 chars → `400`); storage and replay arrive in M7. | §7 rule 11 is a pure request-validation rule. |
| I29 | 2026-10-08 | Problem details: `type` is `about:blank` with a specific `title` (as in §14.3). `400` responses add an `errors` extension member (field → messages) and name the fields in `detail`. Unexpected errors return a generic `500` detail without internals. Correlation id comes from `X-Correlation-ID`/`X-Request-ID` (sanitised) or is generated, and is echoed in the response header. | RFC 7807 extension members are allowed. Avoids leaking internals. |
| I30 | 2026-10-08 | Naive `start_time` values are rejected with `400`; any explicit offset is accepted and normalised to UTC. Output datetimes use `Z`. | A6/§14.1: unambiguous instants only. |
| I31 | 2026-10-08 | Throttling: the booking throttle is keyed by `customer_id` from the body (falling back to client IP), the availability throttle by client IP. Rates come from env (`THROTTLE_BOOKING_RATE`=60/min, `THROTTLE_AVAILABILITY_RATE`=120/min). | §2.1 backpressure. Configurable so load tests can raise limits. |
| I32 | 2026-10-08 | Domain events are dispatched via `transaction.on_commit`, so subscribers never see uncommitted state, even if a caller wraps the handler in an outer transaction (M7 idempotency). Subscriber failures are logged and never fail a committed request. | Strengthens "dispatched after commit" (§4.3). |
| I33 | 2026-10-08 | The API accepts and renders only JSON (`JSONParser`/`JSONRenderer`). There is no browsable API. | No UI in scope; smaller attack surface. |
| I34 | 2026-10-08 | The availability algorithm (§14.4) is a pure domain service, `AvailabilityCalculator`. It takes a `DaySchedule` (busy intervals per bay and per qualified technician) loaded by the read model in 3 queries. Candidate starts are snapped to the same UTC 15-minute grid as `SlotAlignmentPolicy`. | Business rule stays in the domain. Availability can never offer a start that booking would reject (verified by a brute-force test of §7 rule 13). |
| I35 | 2026-10-08 | `GetAppointment` reads Scheduling-owned data from a read model (1 query with bay/technician join), then names from the `CatalogGateway`. It never joins Catalog tables directly. | Keeps the context boundary (A17) on the read side too. The endpoint is not hot. |
| I36 | 2026-10-08 | Availability cache: the key is `(dealership, service_type, local date)` plus a per-(dealership, date) **version** number. Invalidation bumps the version in O(1), orphaning every service type's listing for that day. Data keys expire after `AVAILABILITY_CACHE_TTL_SECONDS` (0 disables caching). The cache is checked *before* catalog lookups, so a hit costs zero DB queries. Unknown ids raise `404` before anything is cached. | §14.4 and A14. Avoids `delete_pattern` scans in Redis. |
| I37 | 2026-10-08 | Invalidation runs as an application event handler (`InvalidateAvailability`) subscribed to `AppointmentConfirmed`/`AppointmentCancelled` in the container. | Booking/cancel handlers stay unaware of caching. Events already exist for exactly this. |
| I38 | 2026-10-08 | Idempotency is the application decorator `Idempotent`, applied in the container. Inside one transaction it (1) **reserves** the key (insert), (2) runs the booking handler, whose unit of work nests as a savepoint, and (3) stores the response. A concurrent duplicate blocks on the unique key and gets `409 idempotency_conflict` once the first commits; if the first fails, the duplicate proceeds. Failed requests store nothing. | §14.5 ("same transaction", "concurrent duplicate loses"). Insert-first avoids doing a booking that would then be rolled back. |
| I39 | 2026-10-08 | The request hash is SHA-256 of the canonical **command** (sorted JSON, datetimes normalised to UTC), not the raw HTTP body. | The same instant written with another offset, or with different key order or whitespace, is the same request. |
| I40 | 2026-10-08 | The stored response is the application DTO as JSON (`serialization.py`), replayed through the same serializer. The HTTP body and `Location` are identical, plus `Idempotent-Replayed: true`. | One rendering path; no HTTP details in the application layer. |
| I41 | 2026-10-08 | Expired keys (older than `IDEMPOTENCY_TTL_HOURS`) are ignored by lookups and replaced on reuse. `manage.py purge_idempotency_keys` deletes them (run it from cron). `DjangoUnitOfWork` keeps a thread-local *stack*, so nested use works. | §14.5 retention. Nesting is required by I38. |
| I42 | 2026-10-08 | `logged_and_measured` is the application decorator `Instrumented`. It needs a `UseCaseTelemetry` port (span + record) and logs with stdlib `logging` (`extra=`). The outcome label is `success` or the error's stable `code`. Infrastructure's `PrometheusTelemetry` implements the port with prometheus_client + the OpenTelemetry API. Retry/conflict counts come from a `BookingObserver` port passed to `BookAppointmentHandler`. | The application stays free of Prometheus/OTel/structlog. Outcome labels have bounded cardinality. |
| I43 | 2026-10-08 | Metrics: `booking_requests_total{outcome}`, `booking_duration_seconds`, `booking_conflicts_total`, `booking_retries_total` (§9), plus `use_case_requests_total{use_case,outcome}`, `use_case_duration_seconds{use_case}`, `availability_cache_requests_total{result}`, and django-prometheus HTTP/DB metrics (DB via the `django_prometheus.db.backends.postgresql` engine wrapper). Histogram buckets bracket the SLOs (0.15/0.3/0.8 s). Cache hit/miss is counted in our cache adapter, since django-prometheus' Redis backend requires `django-redis`. | §9 names. No extra dependency. |
| I44 | 2026-10-08 | Gunicorn runs with `gunicorn.conf.py` (sync workers, `WEB_CONCURRENCY`, graceful timeout 30 s, no access log). `PROMETHEUS_MULTIPROC_DIR` aggregates metrics across workers (cleared `on_starting`, dead workers marked in `child_exit`). Tracing is configured in `wsgi.py`, so each worker (imported post-fork, no preload) has its own exporter thread. | Correct per-worker metrics and traces. |
| I45 | 2026-10-08 | Compose runs `config.settings.prod` (`DEBUG=False`) with a local-only placeholder `SECRET_KEY` that `.env` overrides. Static files (admin, Swagger UI) are collected at image build and served by WhiteNoise, a new dependency, removed from dev/test middleware. | Production-like runtime for load tests (DEBUG would leak memory via query logging) while `make up` still works from a clean clone. |
| I46 | 2026-10-08 | Logs: JSON to stdout via structlog `ProcessorFormatter` (`LOG_FORMAT=console` for humans). Each line has `correlation_id`, `route`, `trace_id`/`span_id`, `use_case`, `outcome`, `duration_ms` and `dealership_id`, with ids only (no PII). `django.request` is raised to ERROR so expected 4xx outcomes don't flood logs. | §9. |
| I47 | 2026-10-08 | Prometheus loads `ops/prometheus-alerts.yml`: booking p95 > 300 ms, 5xx > 0.1%, retries > 20% of bookings, cache hit ratio < 50%. The OTel collector prints spans with the `debug` exporter. | §9 alerting. A real deployment swaps in a tracing backend. |
| I48 | 2026-10-08 | Recorded load results use **k6** (open-model `constant-arrival-rate`, run from its official image on the compose network). Locust stays for interactive exploration (`make locust`). | On the WSL2 test host every Locust variant reported ~120 ms more than the server's own histograms (6.7 ms/request), a plain-Python client (p95 10–12 ms) and k6 (p95 ~9 ms). §3 allows "Locust (or k6)". The open model also matches a TPS target exactly. |
| I49 | 2026-10-08 | Load data comes from a separate `seed_load` (catalog + resources, composed by command name like `seed_demo`) with deterministic ids: dealerships 1001+, 8 bays and 8 technicians each (two skills per technician, 6 qualified per skill), customers/vehicles 100001+. The `docker-compose.load.yml` overlay lifts throttles, because the generator is one client IP. | Repeatable runs; ids computable by the load scripts. |
| I50 | 2026-10-08 | Gunicorn's heartbeat (`worker_tmp_dir`) and the Prometheus multiprocess dir live on `/dev/shm`. | Gunicorn docs: the heartbeat on Docker's overlay filesystem can stall workers. Ruled out as the latency cause above, but kept as best practice. |
| I51 | 2026-10-08 | The concurrency suite includes a test that drops the exclusion constraints (restoring them in `finally`) and asserts the app alone double-books. | Demonstrates decision D2 permanently, not just once. |
| I52 | 2026-10-08 | Default `WEB_CONCURRENCY=4` (it meets the design target with p95 25 ms booking / 10 ms availability at ~0.8 core). The load overlay uses 16 workers for the stress profile: with 4, the CPU-bound sync workers capped throughput at ~330 RPS and queued requests for seconds. With 16, it served 571 RPS at p95 ≤ 39 ms using 17 DB connections. | Tuned from measurement (§2.1 "tune after load testing"). In production, scale pods × workers to the target and keep server connections ≤ 50 via PgBouncer. |
